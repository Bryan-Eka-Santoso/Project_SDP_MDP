2Pola di dua sisi

Hampir semua fitur memakai tiga pola yang sama. Kalau pola ini sudah dipahami, kode fitur baru terasa familiar.

2.1 Rantai middleware backend

Setiap route dilindungi tiga lapis sebelum controller dijalankan. Urutannya penting.

  1. authenticate: baca header Authorization: Bearer …, verifikasi JWT, lalu ambil role dan status akun dari database setiap request (bukan dari isi token), sehingga akun yang diblokir langsung ditolak (ACCOUNT_BLOCKED). Token kedaluwarsa menghasilkan TOKEN_EXPIRED agar Android tahu harus refresh.
  2. authorize(...roles): cek role, kalau tidak cocok 403 FORBIDDEN.
  3. validate({ params, query, body }): Zod memvalidasi input, hasilnya ditaruh di req.validated (Express 5 tidak mengizinkan req.query ditimpa). Gagal → 400 VALIDATION_ERROR dengan details per kolom.

Setelah itu controller hanya memanggil service dan membalas lewat sendSuccess / sendPaginated. Query Prisma dan aturan bisnis hanya ada di service.

2.2 Format response dan error yang seragam

backend/src/utils/response.js
function sendSuccess(res, data, statusCode = 200) {
  return res.status(statusCode).json({ success: true, data });
}

function sendPaginated(res, data, { page, limit, total }) {
  return res.status(200).json({
    success: true, data,
    meta: { page, limit, total, totalPages: Math.ceil(total / limit) },
  });
}

Service tidak pernah menulis response error sendiri; ia melempar AppError(status, code, message, details?), dan errorHandler mengubahnya jadi { success:false, error:{code,message,details?} }. Error tak terduga jadi 500 INTERNAL_ERROR tanpa membocorkan detail.

2.3 Sisi Android: MVVM dan Resource

Fragment hanya merender UiState dan meneruskan klik ke ViewModel. ViewModel memanggil Repository. Repository membungkus panggilan Retrofit dengan errors.call { … } (ApiErrorMapper) sehingga hasilnya selalu Resource.Success(data) atau Resource.Error(pesanIndonesia); tidak ada exception yang bocor ke UI. Untuk IMPORT_INVALID, daftar kesalahan per baris ikut dibawa di Resource.Error.importErrors.

3.1 Sisi backend

  • Anti-penebakan akun. Jika email tidak ada, server tetap menjalankan bcrypt.compare terhadap hash palsu (DUMMY_HASH) supaya waktu respons tidak membedakan "akun tidak ada" dan "password salah".
  • Refresh token tidak disimpan mentah. Yang disimpan di database adalah hash SHA-256-nya; token asli (48 byte acak) hanya dikirim ke perangkat.
  • Rotasi + deteksi pemakaian ulang. Setiap refresh menerbitkan pasangan token baru dan mencabut yang lama. Kalau token yang sudah dicabut dipakai lagi (tanda token bocor), semua sesi akun itu dicabut.
  • Logout idempotent: mencabut refresh token dan menghapus token perangkat FCM supaya akun lama tidak lagi menerima push di HP itu.
  • Ubah password mencabut sesi di perangkat lain, lalu menerbitkan token baru untuk perangkat yang sedang dipakai.

3.2 Sisi Android: token otomatis diperbarui

AuthInterceptor menambahkan header Authorization ke semua request kecuali /auth/login, /auth/refresh, dan /auth/logout. Bila server membalas 401, OkHttp memanggil TokenAuthenticator secara otomatis:

android/…/data/remote/TokenAuthenticator.kt (inti)
override fun authenticate(route: Route?, response: Response): Request? {
    if (responseCount(response) >= 2) return null          // jangan loop tanpa akhir
    // ... endpoint auth tidak di-refresh ...
    return synchronized(lock) { runBlocking {
        val current = sessionManager.getAccessToken()
        val used = response.request.header("Authorization")?.removePrefix("Bearer ")
        // request lain sudah refresh duluan: pakai token terbaru saja
        if (!current.isNullOrBlank() && used != current) return@runBlocking retryWith(current)

        val refreshToken = sessionManager.getRefreshToken() ?: return@runBlocking null
        try {
            val tokens = refreshApi.refresh(RefreshRequest(refreshToken)).data!!
            sessionManager.saveTokens(tokens.accessToken, tokens.refreshToken)
            retryWith(tokens.accessToken)                       // ulangi request asli
        } catch (e: HttpException) {
            if (e.code() in 400..403) {                         // refresh ditolak server
                sessionManager.clearSession()
                sessionEvents.notifyExpired()                   // MainActivity kembali ke login
            }
            null
        } catch (e: Exception) { null }                         // gangguan jaringan: sesi JANGAN dihapus
    } }
}
Kenapa synchronized? Kalau tiga request gagal 401 bersamaan, hanya yang pertama benar-benar refresh. Dua lainnya melihat token sudah berubah dan langsung memakainya. Tanpa ini, refresh kedua akan memakai refresh token lama dan dianggap pemakaian ulang, sehingga semua sesi dicabut.

  • Ganti dalam satu transaksi: hapus rentang lama lalu isi yang baru, jadi layar tidak pernah melihat setengah data. Bila refresh gagal (offline), cache lama tetap tampil.

  • Jadwal yang dikirim server sudah setelah perubahan jadwal per tanggal diterapkan (dibatalkan, dipindah, guru pengganti), lihat bagian 7.

5Admin: kelola slot jadwal dan cek bentrok

F-JDW-01F-JDW-03

Admin membuat slot mingguan (hari + jam + ruang untuk satu penugasan guru-mapel-kelas). Sebelum disimpan, slot dicek bentrok. Aturan bentrok dipisah ke satu file murni (schedules.conflicts.js) agar dipakai ulang oleh impor Excel dan perubahan jadwal.

5.1 Apa itu bentrok

Dua slot pada hari yang sama dengan jam yang beririsan dianggap bentrok bila salah satu terpenuhi:

AlasanArti
TEACHERGuru yang sama mengajar di dua tempat sekaligus
CLASSKelas yang sama punya dua pelajaran sekaligus
STUDENTAda siswa yang sama di dua kelas berbeda (mis. kelas reguler + kelas paket)
ROOMRuangan dipakai dua kegiatan sekaligus

Jam yang bersambung tidak bentrok: selesai 08.30 dan mulai 08.30 aman, karena rentangnya setengah terbuka [mulai, selesai).

backend/src/modules/schedules/schedules.conflicts.js
function overlaps(a, b) {
  return a.startTime.getTime() < b.endTime.getTime() && b.startTime.getTime() < a.endTime.getTime();
}

function detectConflicts(candidate, others, sharedClassIds = new Set()) {
  const details = [];
  for (const other of others) {
    if (other.dayOfWeek !== candidate.dayOfWeek || !overlaps(candidate, other)) continue;

    const reasons = [];
    if (other.teacherId === candidate.teacherId) reasons.push('TEACHER');
    if (other.classGroupId === candidate.classGroupId) reasons.push('CLASS');
    else if (sharedClassIds.has(other.classGroupId)) reasons.push('STUDENT');
    if (other.roomId === candidate.roomId) reasons.push('ROOM');

    for (const reason of reasons) {
      details.push({ field: FIELD_BY_REASON[reason], reason, slotId: other.id,
                     message: describe(reason, other) });   // kalimat Indonesia untuk admin
    }
  }
  return details;
}

Fungsi ini murni (tidak menyentuh database), jadi mudah diuji. Pembungkusnya yang melakukan query:

backend/src/modules/schedules/schedules.conflicts.js
async function findSlotConflicts(db, candidate, { semesterId, excludeSlotId } = {}) {
  const rows = await db.scheduleSlot.findMany({
    where: {
      ...(excludeSlotId ? { id: { not: excludeSlotId } } : {}),  // saat edit: jangan bandingkan dgn diri sendiri
      dayOfWeek: candidate.dayOfWeek,
      startTime: { lt: candidate.endTime },     // filter irisan jam langsung di SQL
      endTime: { gt: candidate.startTime },
      teachingAssignment: { semesterId },
    },
    select: slotForConflict,
  });
  return conflictsAgainst(db, candidate, rows.map(flatten));
}

Jika ada bentrok, service melempar AppError(409, 'SCHEDULE_CONFLICT', …, details). Android memetakan details menjadi daftar pesan di formulir (ApiErrorMapper.DETAIL_CODES memuat SCHEDULE_CONFLICT), sehingga admin tahu persis slot mana yang bentrok.

6.1 Cek bentrok untuk banyak baris tanpa query per baris

findConflictsInBatch memuat semua slot semester satu kali (loadSemesterSlots), mengelompokkannya per hari, lalu memeriksa kandidat berurutan. Jadwal yang persis sama dengan yang ada dilaporkan sekali sebagai DUPLICATE, bukan sebagai tiga bentrok sekaligus.

7Perubahan jadwal per tanggal dan notifikasi push

F-JDW-04F-NTF-01F-NTF-02

Perubahan tidak mengubah slot mingguan; ia menempel pada satu slot di satu tanggal (ScheduleChange, maksimal satu per slot per tanggal). Menghapus perubahan = jadwal tanggal itu kembali normal. Ada tiga jenis:

JenisEfek pada tanggal itu
CANCELSlot hilang dari jadwal
SUBSTITUTEGuru diganti substituteTeacher
RESCHEDULEJam dan/atau ruangan diganti

7.1 saveChange: urutan pemeriksaan

  1. Muat slot; kalau tidak ada → 400 pada kolom scheduleSlotId.
  2. ensureDateMatchesSlot: tanggal harus di dalam semester dan jatuh pada hari yang sama dengan hari slot (hari Senin, bukan Selasa).
  3. SUBSTITUTE: guru pengganti harus ada, aktif, dan bukan guru asli. RESCHEDULE: ruangan harus valid dan harus benar-benar berbeda dari jadwal asli.
  4. ensureNoConflictOnDate: cek bentrok pada tanggal itu, dengan jadwal lain yang sudah diubah ikut dihitung (lihat 7.2). CANCEL tidak perlu dicek.
  5. upsert berdasarkan kunci gabungan (scheduleSlotId, date) → membuat atau memperbarui.
  6. Kirim notifikasi (tidak ditunggu).

findConflictsOnDate mengambil semua slot di hari itu (tanpa filter jam, karena jam slot lain bisa saja sudah dipindah), menerapkan perubahan tanggal itu ke masing-masing lewat applyChange, lalu membandingkan:

function applyChange(slot, change) {
  if (!change) return slot;
  if (change.type === 'CANCEL') return null;               // slot dibatalkan: tidak bisa bentrok
  if (change.type === 'SUBSTITUTE')
    return { ...slot, teacherId: change.substituteTeacherId, teacherName: change.substituteTeacher.user.name };
  return { ...slot,                                          // RESCHEDULE
    startTime: change.newStartTime ?? slot.startTime,
    endTime: change.newEndTime ?? slot.endTime,
    roomId: change.newRoomId ?? slot.roomId, roomName: change.newRoom?.name ?? slot.roomName };
}

const others = rows.map((row) => applyChange(flatten(row), row.changes[0])).filter(Boolean);

8Tagihan

F-BYR-01F-BYR-02F-BYR-03

Tagihan hanya informasi: tidak ada pembayaran di aplikasi. Admin mengunggah Excel berisi tagihan per siswa; siswa, wali murid, dan wali kelas (untuk kelasnya) bisa melihat sesuai cakupan datanya.

  • Impor (bills.import.service.js) memakai kerangka yang sama dengan impor jadwal: validasi semua baris, importInvalid bila ada yang salah, simpan dalam satu $transaction (batas 20.000 baris). Bedanya, ini upsert: tagihan dengan pasangan NIS + kode tagihan yang belum ada dibuat, yang sudah ada diperbarui, dan yang tidak berubah dihitung unchanged. Response berisi created, updated, unchanged, notifiedStudents, sehingga mengunggah file yang sama dua kali aman.
  • Status "terlambat" tidak disimpan. Ia dihitung saat dibaca: isOverdue = status === 'UNPAID' && dueDate < today. Filter ?overdue=true menerjemahkannya ke kondisi Prisma { status:'UNPAID', dueDate:{ lt: todayDate } }. Dengan begitu tidak perlu cron untuk mengubah status.
  • Pemberitahuan keterlambatan (F-BYR-03). Setelah transaksi impor berhasil, tagihan UNPAID yang sudah lewat jatuh tempo dikelompokkan per siswa (overdueByStudent) dan dikirim satu notifikasi BILL_OVERDUE per siswa ke siswa itu dan wali muridnya lewat notify().   • Cakupan data ada di bills.policy.js: siswa = diri sendiri, wali murid = anaknya, wali kelas = siswa di kelas yang homeroomTeacherId-nya dia pada tahun ajaran aktif (bukan flag isHomeroomTeacher), admin = semua.

9.2 Android: ReportViewModel generik

Kelas dasar ini menangani filter, halaman, total, dan ekspor. Turunannya (ScheduleChangeReportViewModel, TeachingLoadReportViewModel) hanya mengisi empat fungsi abstrak.

android/…/ui/admin/report/ReportViewModel.kt (inti)
abstract class ReportViewModel<R : Any, F : Any>(initialFilter: F) : ViewModel() {

    protected abstract suspend fun fetch(page: Int, filter: F): Resource<ReportPage<R>>
    protected abstract suspend fun export(filter: F, destination: String): Resource<Boolean>
    protected abstract suspend fun fetchOptions(): Resource<ReportOptions>
    protected abstract fun idOf(row: R): Int          // untuk membuang duplikat antar halaman

    fun refresh() {
        loadJob?.cancel()                              // pemuatan lama dibatalkan
        loadOptionsOnce()                              // pilihan filter (guru, kelas) cukup sekali
        loadJob = viewModelScope.launch {
            _uiState.update { it.copy(isLoading = true, errorMessage = null) }
            when (val result = fetch(1, _uiState.value.filter)) {
                is Resource.Success -> { nextPage = 2; _uiState.update { it.copy(rows = result.data.items, ...) } }
                is Resource.Error   -> _uiState.update { it.copy(isLoading = false, errorMessage = result.message) }
            }
        }
    }

    /** Ubah filter lalu muat ulang; tidak melakukan apa-apa bila hasilnya sama. */
    protected fun updateFilter(transform: (F) -> F) {
        val current = _uiState.value.filter
        val changed = transform(current)
        if (changed == current) return
        // daftar lama dikosongkan: bila gagal, tidak ada baris dari filter sebelumnya yang tersisa
        _uiState.update { it.copy(filter = changed, rows = emptyList(), total = 0, hasMore = false, isLoading = true) }
        refresh()
    }
}
  • Halaman berikutnya (loadMore) dimuat saat daftar digulir ke bawah; baris yang sudah ada dibuang berdasarkan idOf, karena data bisa bergeser antar halaman.
  • Layar kosong vs error dibedakan: isEmpty = rows.isEmpty() && !isLoading && errorMessage == null. Gagal memuat tidak pernah tampil sebagai "tidak ada data".
  • Layar lebar: kartu tampil 2 kolom di tablet lewat values-sw600dp/integers.xml.
  • Tombol Laporan hanya muncul di Profil bila Profile.canViewReports (role ADMIN); backend tetap yang menjaga hak akses.
